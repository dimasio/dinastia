# Git

## Правила

- **Коммит, push, PR — только по прямой просьбе человека** в этой задаче. «Сделай фичу» — не просьба коммитить.
- Работа — в ветке, не в `main`: `<тип>/<slug>`, типы `feat`, `fix`, `chore`, `core`, `docs`
  (`feat/quiz-timer`, `core/rls-helpers`).
- `main` всегда зелёный; мерж — squash через PR после зелёного CI.
- Не коммитить: `.env*` (кроме `.env.example`), ключи, дампы БД, `node_modules`, артефакты сборки, личные данные
  учеников, скриншоты с реальными данными.
- Не переписывать опубликованную историю (`push --force` в общие ветки) без просьбы.

## Сообщение коммита

Conventional Commits, описание на русском:

```
feat(assessments): таймер попытки теста

Серверный срок started_at + time_limit_sec, автосдача задачей
assessments.expire-attempts. Карточка: docs/tasks/phase-3-assessments/changes/quiz-timer.md
```

Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`, `build`, `ci`; область — модуль (`courses`),
`kernel`, `ui`, `blocks`, `questions`, `web`, `docs`. Ломающее изменение контракта — `!` после области и
`BREAKING CHANGE:` в теле. Подпись агента — по системным правилам (Co-Authored-By).

## Поэтапная проверка

В `change-workflow` одобренные шаги копятся в staging (`git add <файлы шага>`), текущий шаг — unstaged. Добавляй
только файлы своего шага; посторонние изменения в рабочей копии не трогай.

## Pull request

```markdown
## Что

<1–3 предложения>
## Зачем

Карточка/задача: <ссылка>
## Как проверить

1. `pnpm db:reset && pnpm db:seed`
2. войти teacher@demo.local, …
## Чек-лист

- [ ] pnpm check
- [ ] e2e <сценарий>
- [ ] миграции: нет / есть (обратимы? данные?)
- [ ] контракт: совместим / ломает (кого)
- [ ] docs: domain.md / скилл / release notes
```

## Параллельная работа

Несколько агентов одновременно — каждый в своём git worktree и ветке (скилл `agent-collaboration`); миграции
двух веток с одинаковым номером — при ребейзе перегенерировать свою (`pnpm db:generate` после `git rebase main`,
старую удалить — она ещё не в main).

## Остановись и спроси, если

- нет репозитория/remote, а просят PR;
- конфликт ребейза в чужом коде или в миграциях из main;
- в diff попали секреты или персональные данные.
