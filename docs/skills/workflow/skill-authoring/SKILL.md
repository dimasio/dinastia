# Написание скиллов

Правила раскладки — `docs/skills/README.md`. Этот скилл — как писать хорошо.

## Нужен ли новый скилл

| Ситуация | Что делать |
|---|---|
| новый вид работы, у которого свой контракт (новый реестр, новый процесс) | новый скилл |
| в существующем виде появилась опция/правило | правка существующего скилла |
| знание — формат или модель данных | спека (`docs/specs`), скилл ссылается на неё |
| разовое знание задачи | `docs/tasks/<задача>/notes` |
| агент повторяет одну и ту же ошибку | правило в «Правила»/«Не делай» нужного скилла + проверка в `pnpm check`, если можно автоматизировать |

## Принципы (из опыта GaskarFM)

- **Команды вместо чтения кода**: каждый шаг — конкретная команда (`pnpm gen:*`, `pnpm check`, `pnpm test -- …`).
- **Генератор/шаблон вместо «посмотри на соседа»**: пример в скилле = вывод генератора или реальный файл.
- **Сначала смысл, потом формат**: как это работает в рантайме, затем поля и шаги.
- **Явное условие окончания** и **точки остановки** — что агент не решает сам.
- **Для небольших моделей**: короткие нумерованные шаги, таблицы, без отсылок к возможностям конкретного агента.
- **Одно знание — в одном месте**: не копируй спеку, ссылайся.

## Шапка

```yaml
---
name: <имя>          # = путь внутри уровня через «-»; уникально
description: <Что это в Dinastia — перечисление ключевых понятий, файлов и команд; Использовать для «фразы
  пользователя», «ещё фразы»…>
---
```

`description` — главное: по нему агент выбирает скилл. Включи слова, которыми человек ставит задачу, и пути файлов.
1–4 предложения.

## Тело

```markdown
# <Название>

> Статус: целевой — сверить с кодом в фазе N.      ← только если механизма ещё нет

<1–3 предложения: что это и ссылки на спеку>

## Как устроено / Описание     код-пример, таблица опций
## Шаги                        1…N с командами
## Правила / Не делай
## Готово, когда
## Остановись и спроси, если
```

Объём — до ~250 строк. Больше — раздели (`<вид>` → `<вид>-<часть>`) или вынеси справочник в спеку.

## Шаги

1. Уровень и имя (продуктовые имена — от человека).
2. Написать `docs/skills/<уровень>/<путь>/SKILL.md`.
3. Примеры: скопировать из реального кода и проверить, что компилируются (или отметить «целевой»).
4. Строка в таблице `AGENTS.md` (нужный раздел).
5. `pnpm skills:link` (до фазы 0 — `bash tools/skills-link.sh`), `pnpm docs:check`.
6. Проверка «холодным» агентом: поручи исполнителю (без контекста) типовую задачу по скиллу и посмотри, где он
   ошибся — поправь скилл (скилл `agent-collaboration`).

## Сверка с кодом

Механизм изменился → в той же задаче: найди скиллы, где он упомянут (`grep -rl "<имя>" docs/skills`), поправь
сигнатуры, пути, команды, примеры.

## Остановись и спроси, если

- скилл требует решения, которого нет в архитектуре/спеке — сначала решение;
- новый продуктовый процесс без имени от человека.
