# Зависимости

## Сначала — не ставить

1. Есть ли решение в стеке (`architecture.md` §1) или в `packages/*`? (даты — `date-fns`? нет: форматтеры
   `@dinastia/i18n`; HTTP-клиент — `@/kernel/http`; валидация — zod).
2. Это 20 строк своего кода? — напиши сам.
3. Нужна только в одном модуле — всё равно ставится в пакет-приложение (`apps/api` или `apps/web`), не в корень.

## Критерии

| Критерий | Требование |
|---|---|
| поддержка | релиз за последние 12 месяцев, живые issues, не один автор без активности |
| лицензия | MIT, Apache-2.0, BSD, ISC; GPL/AGPL/SSPL — нельзя без человека |
| типы | встроенные TS-типы |
| формат | ESM; для клиента — tree-shaking, размер (bundlephobia) |
| безопасность | без postinstall-скриптов с сетью, без телеметрии; `pnpm audit` чистый |
| доступность | пакет и его сервисы работают из РФ; не SaaS-зависимость, которую могут отключить |

## Шаги

1. Выбор — 1–3 кандидата с таблицей критериев; значимая библиотека (влияет на архитектуру, ядро, данные) — показать
   человеку и записать `D-NNN`.
2. Версия — проверь актуальную (`pnpm view <pkg> version`), не по памяти.
3. Общая для нескольких пакетов — в `pnpm-workspace.yaml → catalog:` и `"<pkg>": "catalog:"` в package.json.
4. `pnpm --filter <app> add <pkg>`; dev-зависимость — `-D`.
5. `pnpm check`; для клиента — размер бандла (`pnpm --filter web build` → отчёт).

## Обновления

- Еженедельно (задача CI или вручную): `pnpm outdated`, патчи и миноры — пачкой с `pnpm check` и e2e.
- Мажор — отдельная задача: changelog, миграционный гайд, правка скиллов, если меняются примеры.
- Уязвимость (`pnpm audit`) high/critical — сразу, отдельной веткой.

## Остановись и спроси, если

- нужна платная библиотека или SaaS;
- лицензия не из списка;
- библиотека заменяет выбор из `architecture.md` §1.
