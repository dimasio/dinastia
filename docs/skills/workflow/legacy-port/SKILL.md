# Перенос из GaskarFM

GaskarFM — только **источник знаний**. Код, YAML-форматы, ggid, `factory`/`gQuery` не переносятся (D-017).
Карта концепций — `docs/specs/legacy-mapping.md`.

## Где искать в GaskarFM

| Что                          | Путь (от `gaskarfm/app/`)                              |
| ---------------------------- | ------------------------------------------------------ |
| точка входа, правила         | `../AGENTS.md`, `docs/README.md`                       |
| скиллы (что и как устроено)  | `docs/skills/{product,platform,core}/<скилл>/SKILL.md` |
| спеки форматов и решения     | `docs/specs/platform/*.md`, `docs/specs/decisions.md`  |
| описание процессов для людей | `docs/guide/product/**`                                |
| модули (классы, формы, код)  | `modules/<модуль>/{classes,forms,…}`                   |
| тесты                        | `tests/**`                                             |

GaskarFM **только читать**: не запускать его команды, не менять файлы, не подключаться к его БД и стендам.

## Шаги

1. **Найти.** Старый скилл по теме (`grep -ril "<термин>" gaskarfm/app/docs/skills`), затем модуль и классы
   (`modules/*/classes/**/class.yaml` с `title` по теме).
2. **Извлечь** в `docs/tasks/<задача>/notes/legacy-<тема>.md`:
   - назначение и пользователи процесса;
   - сущности и важные поля (смысл, а не `alias`);
   - статусы и переходы, кто их делает;
   - правила и проверки (из `class.js`: `_Require`, `_ReadOnly`, `_onChanged`, методы);
   - права (`restrictions`, ключи безопасности);
   - автоматизация (шаблоны задач, трансформации), отчёты;
   - **подводные камни**: долг миграции, костыли, комментарии «временно», баги из `docs/tasks`.
     Каждый пункт — со ссылкой `путь:строка` в GaskarFM.
3. **Отфильтровать.** Что относится к FM/ERP и не нужно LMS — пометить «не переносим» с причиной. Что спорно —
   вопрос человеку.
4. **Сопоставить.** По `legacy-mapping.md`: класс → таблица + контракт, форма → ресурс или экран, ключ → разрешение,
   шаблон задачи → `defineJob` и т.д.
5. **Спроектировать.** Новый процесс — `feature-design`; доработка существующего — `change-workflow`. Заметка
   `legacy-<тема>.md` — источник в разделе «Запрос».
6. **Записать происхождение.** В спеке процесса — строка «Основано на GaskarFM: <скилл/модуль>, отличия: …».
   Новое соответствие концепций — строка в `legacy-mapping.md`.

## Не делай

- не копируй код `class.js`/handlers и названия полей «как есть» — имена по нашим правилам (`db-schema`);
- не переноси обходы ограничений старой платформы (то, что там делалось через `privateState`, сокеты, ggid-хаки);
- не обещай совместимость данных — миграции данных из GaskarFM вне рамок, если человек не сказал иначе.

## Готово, когда

Заметка с правилами и ссылками есть, отфильтрованное согласовано с человеком, дальше работа идёт по
`feature-design`/`change-workflow`.

## Остановись и спроси, если

- старый процесс и LMS-процесс расходятся по смыслу (одно слово — разные вещи);
- нужен перенос **данных** из GaskarFM;
- правило в старом коде противоречит старому скиллу — что считать верным.
