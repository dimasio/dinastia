# Изменение продукта

Единица работы — **изменение**: одна фича или группа багов, которые чинятся одной правкой. Изменения — строго по
одному: следующее не начинается, пока у текущего не закрыты все шаги.

## Шаги

| Шаг               | Что                                                                                                                               | Где                                   | Кто                           |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- | ----------------------------- |
| 1. Запрос         | что сейчас (по спеке `docs/specs/domain.md` и коду, `путь:строка`), что нужно, источник, вопросы                                  | карточка §1                           | агент                         |
| 2. Архитектура    | какие модули, таблицы, контракты, экраны, блоки меняются; варианты и выбранный; миграции; риски; что не трогаем; **блокеры ядра** | карточка §2                           | агент                         |
| 3. Целевая спека  | дельта спеки: раздел → было → станет; новые события, права, статусы                                                               | карточка §3                           | агент; **человек утверждает** |
| 4. Разработка     | правки по скиллам платформы, перечень изменений, проверки, что не проверено                                                       | карточка §4                           | агент                         |
| 5. Спека и скиллы | целевой текст перенесён в `docs/specs/domain.md`; продуктовый скилл `lms-*` поправлен                                             | карточка §5                           | агент                         |
| 6. Release notes  | что изменилось для ролей школы и учеников, как проверить                                                                          | `docs/guide/product/release-notes.md` | агент                         |

Разработка (шаг 4) — **только после утверждения шагов 1–3**. После шага 3 остановись и жди «утверждаю» / правок.

Мелочь без изменения поведения (опечатка, рефакторинг без эффекта, обновление зависимости) — без карточки, но с
планом в чате.

## Карточка

`docs/tasks/<задача>/changes/<slug>.md`; задачи нет — спроси человека, к какой задаче отнести (или создай
`docs/tasks/<slug>/task.md` с его согласия).

```markdown
# <Изменение>: <коротко>

Задача: [<задача>](../task.md) · Шаг: 1 | 2 | 3 | 4 | 5 | 6 — готово

## 1. Запрос

Источник. Что сейчас (спека, код `путь:строка`). Что нужно. Вопросы и ответы человека (дата).

## 2. Архитектура

| Слой | Что меняется | Скилл |
| БД | таблица/колонка, миграция (данные?) | db-schema |
| Контракт | процедуры, схемы — ломает ли клиентов | api-endpoints |
| Сервис | правила | data-access |
| Права | разрешения, роли | permissions |
| UI | экраны, ресурсы, блоки | admin-resource / web-screens / lesson-blocks |
| События/задачи | | events-automations / background-jobs |
Варианты → выбранный и почему. Риски. Что не трогаем. Блокеры ядра → запросы `docs/tasks/requests/`.

## 3. Целевая спецификация

| Раздел `domain.md` | Было | Станет |
Утверждено: <кто, дата>.

## 4. Разработка

| Файл (`путь:строка`) | Что | Зачем |
Проверки: `pnpm check` — ok; e2e `<сценарий>` — ok. Не проверено: … Миграции: …

## 5. Спека и скиллы

Что перенесено.

## 6. Release notes

Ссылка на запись.
```

## Поэтапная проверка через git

1. Сделать шаг, правки оставить unstaged; остановиться, ждать проверки.
2. Перед следующим шагом — `git add` **только** одобренных правок предыдущего шага.
3. Просят поправить текущий шаг — правка остаётся в нём, без staging.
4. Коммит и push — только по прямой просьбе.

## Готово, когда

Все шесть шагов отмечены в карточке, `pnpm check` зелёный, e2e-сценарий изменения зелёный, `domain.md` и скилл
процесса описывают новое поведение.

## Остановись и спроси, если

- источник требования неясен или противоречит спеке;
- изменение требует миграции, удаляющей данные, или ломает контракт API;
- нужен новый процесс/роль/сущность — имя даёт человек;
- архитектура упирается в ядро (блокер).
