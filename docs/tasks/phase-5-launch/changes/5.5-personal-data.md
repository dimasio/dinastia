# 5.5: персональные данные — согласия, экспорт и обезличивание ученика, удаление школы

Задача: [phase-5-launch](../task.md) · Шаг: 4 — разработка

## 1. Запрос

Источник — роадмап 5.5 «Юридическое и ПДн: тексты согласия, политики, оферты (от человека); экспорт и обезличивание ученика,
удаление школы (скилл `personal-data`)»; правила скилла `personal-data` §5, §7, §8.

Что сейчас (сверка с кодом):

| Что | Есть | Где |
| --- | --- | --- |
| согласие владельца школы с офертой и политикой Dinastia | да, версия `draft-2026-10`, текста нет — только фраза на форме | `modules/schools/service.ts:28`, `kernel/legal.ts`, `auth:consent` |
| страницы оферты и политики | **нет** | — |
| согласие ученика на обработку ПДн школой | **нет** (вид `pd_processing` в enum есть, не пишется) | `join.$token.tsx`, `kernel/auth/schema.ts:87` |
| юридические реквизиты школы (оператор ПДн, политика, контакт) | **нет**; настроек школы нет ни одной (реестр `defineSettings` есть, экрана нет) | `kernel/settings/` |
| экспорт данных ученика | **нет**; есть выгрузка учеников курса в xlsx | `kernel/exports/`, `modules/learning/exports.ts:25` |
| обезличивание ученика | **нет**; есть только блокировка участника | `schools.members.setStatus`, `member_status` = `active`/`blocked` |
| удаление школы | **нет**; в `schools` есть `status` (`deleted`) и `deletion_requested_at`, право `schools.delete` (только owner) | `packages/db/src/schools.ts`, `modules/schools/permissions.ts` |
| экран учеников школы | **нет**; ученики видны по курсам (`/admin/courses/<id>/learners`) | — |

Где лежат ПДн ученика в школе: `users` (имя, почта, аватар — глобально), `sessions`/`accounts` (глобально), `members` (аватар),
`consents`, `enrollment_invites.email`, ответы тестов (`quiz_answers.text_value`), работы и переписка (`submissions.body`,
`submission_comments.body`) и их файлы, `certificates.student_name` и PDF, `audit_log.ip`, `files.name`.

Препятствия, которые определяют решение:

- `members.user_id → users` — `restrict`, `audit_log.actor_member_id → members` — без каскада, а журнал неизменяем (D-048): строку
  участника удалить нельзя, только обезличить.
- имя ученика везде берётся join-ом `members → users.name`; один человек может быть в нескольких школах — менять `users` нельзя, если
  у него есть другие членства.

Нужно: школа (оператор ПДн) исполняет запросы ученика — выдать его данные и удалить их; ученик даёт согласие при присоединении;
владелец может удалить школу со всеми данными.

### (в) Обезличивание ученика

Выбран вариант **«отвязка на заглушку»**: в школе создаётся пользователь-заглушка («Удалённый ученик», почта
`deleted+<id>@deleted.invalid`, без входа), `members.user_id` переводится на неё, участник получает статус `deleted`. Все экраны,
которые берут имя через `users`, сразу показывают «Удалённый ученик» — без правок в каждом запросе. Если у человека больше нет
членств — его `users` удаляется (сессии, аккаунты, согласия — каскадом).

| Слой | Что меняется | Скилл |
| --- | --- | --- |
| БД | `member_status` += `deleted`; `users.deleted_at` (заглушки не входят и не попадают в поиск оператора) — **миграция** (добавление значения enum и колонки). Функция БД `audit_forget_ip(member_id)` (`SECURITY DEFINER`, владелец `app_owner`): обнуляет только `ip` в журнале этого участника — журнал в остальном остаётся неизменяемым | `db-schema`, **ядро** |
| Сервис | `anonymizeMember` (ядро `kernel/members` + функции модулей `learning`, `assessments`, `certificates`, как требует скилл): удаляются файлы работ и комментариев ученика, аватар, приглашения на его почту, согласия этой школы; тексты его ответов, работ и комментариев заменяются на «Удалено»; **оценки, баллы, статусы и прогресс сохраняются** (статистика школы); сертификаты — имя «Удалённый ученик», PDF удаляется, сертификат **аннулируется** (проверка по номеру — «аннулирован»). Одна транзакция + удаление объектов S3 задачей | `data-access`, `files-media` |
| Контракт | `schools.members.anonymize({ memberId, confirm })` — только для участников с ролью `student`; сотрудника сначала лишают роли | `api-endpoints` |
| Права | `schools.pd.manage` (owner, admin); журнал `schools.member.anonymized` (без имени — только id) | `permissions` |
| UI | Экран **«Ученики школы»** `/admin/students` (новый, ресурс: имя, почта, курсы, дата присоединения; поиск) с действиями строки «Выгрузить данные» и «Удалить данные ученика» (диалог: что удалится и что останется, ввод слова «удалить»). Ученик в профиле видит: «Чтобы удалить данные, напишите школе: <почта из реквизитов>» | `admin-resource`, `ux-writing` |

### (г) Удаление школы

| Слой | Что меняется | Скилл |
| --- | --- | --- |
| Запрос | `schools.requestDeletion({ slug })` (ввод адреса школы для подтверждения), право `schools.delete` (owner): `status` → `deleted`, `deletion_requested_at` = сейчас. **30 дней школа закрыта** для учеников и сотрудников (страница «Школа удаляется»), владелец видит её в «Мои школы» на корневом домене с кнопкой «Отменить удаление» (`schools.cancelDeletion`). Письма владельцу: при запросе и за 3 дня до удаления | `lms-school`, `notifications` |
| Удаление | задача ядра `schools.purge` раз в сутки: школы с `deletion_requested_at` старше 30 дней → объекты S3 по префиксу `schools/<id>/`, затем все тенантные строки (таблицы из `rls-coverage`) от роли `app_owner`, затем `schools`; пользователи без других членств (кроме владельцев — их данные обрабатывает Dinastia как оператор) удаляются. Повторяемо: упавшая задача продолжит с места | **ядро** `kernel/db`, `background-jobs` |
| Бэкапы | данные остаются в бэкапах до истечения срока их хранения (5.3) — фраза в политике | — |

### Тесты

Интеграционные: согласие пишется при присоединении и без него присоединиться нельзя; экспорт содержит данные ученика и не содержит
чужих (другой ученик, другая школа) — в т. ч. файлы; ученик выгружает только себя; обезличивание — во всех таблицах из перечня §1 нет
имени, почты, текстов и файлов, оценки и прогресс на месте, человек в другой школе не задет, без других членств — `users` удалён;
журнал без IP; удаление школы — после 30 дней в БД и S3 ничего от школы, соседняя школа не задета, отмена работает. Тест-страж: новая
`pii()`-колонка в тенантной таблице без обработки в `anonymizeMember` — падение. e2e `personal-data.spec.ts`: присоединение с
согласием → ученик скачивает данные → администратор обезличивает → в списке учеников курса «Удалённый ученик».

### Варианты (отвергнуты)

- *Хранить имя в `members` и править все запросы* — десятки мест, легко забыть новое; заглушка даёт то же одним изменением.
- *Обезличивать `users` всегда* — задело бы человека в других школах.
- *Удалять строки работ и попыток* — ломает статистику и агрегаты школы, скилл требует их сохранить.
- *Школа работает 30 дней до удаления* — данные продолжают обрабатываться после решения владельца; закрыть сразу — понятнее и
  безопаснее, отмена остаётся.
- *Ученик удаляет себя сам* — оператор ПДн школа; запрос идёт через неё (как в Skillspace/GetCourse). Можно добавить позже кнопкой
  «Запросить удаление» с письмом администраторам.

Риски: удаление школы — необратимо и работает от `app_owner` в обход RLS: префикс S3 и `school_id` берутся только из строки
`schools` со статусом `deleted` и сроком > 30 дней, тест с соседней школой. Заглушка-пользователь — не должна входить: у неё нет
`accounts`, `deleted_at` проверяется при входе.

Что не трогаем: тексты оферты и политики (даёт владелец), сроки хранения бэкапов (5.3), консоль оператора (5.6), удаление аккаунта
владельцем школы на корневом домене (после MVP).

**Ядро** (в пределах пункта 5.5 — разрешено задачей): `kernel/exports` (zip), `kernel/members` (обезличивание), `kernel/db`
(очистка школы, `audit_forget_ip`), `kernel/legal.ts`.

**Миграции** (только добавление): `schools_settings`; `member_status += deleted`; `users.deleted_at`; функция `audit_forget_ip`.
**Контракт**: `join.accept` и `invitations.accept` получают обязательное `consent` — меняется вход (клиент — только наш веб).
