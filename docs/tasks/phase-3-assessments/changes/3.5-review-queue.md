# 3.5: очередь проверки, экран проверки и переписка

Задача: [phase-3-assessments](../task.md) · Шаг: 6 — готово

## 1. Запрос

Источник — роадмап 3.5 «Очередь проверки для преподавателя/куратора: фильтры по курсу, группе, статусу; экран проверки с
перепиской».

Что сейчас:

- Задания (3.4): сдачи со статусами, переходы только через `transition`, `assignment.review` (принять / на доработку /
  отклонить + комментарий) для admin и teacher, комментарии проверяющего (`submission_comments`) видны ученику; события
  `submission.submitted`, `submission.reviewed`. Экрана проверки нет — проверять можно только через API.
- Ресурс-фреймворк (`admin-resource`): списки с поиском, фильтрами, действиями; ресурс на курс — фабрика (банк вопросов, 3.1).
- Письма: `defineEmail` на `react-email`, отправка задачей из подписчика события (`notifications`, `events-automations`).
- Куратор: домен велит ему видеть и проверять **только свои группы** (`group_curators`), но потоки и группы появляются в фазе 4.
  Демо фазы 3 требует, чтобы куратор отправил работу на доработку и принял её.
- Нет: очереди, экрана проверки, ответов ученика в переписке, файлов к комментариям, писем о результате, пункта меню.

Нужно: проверяющий видит все работы, ждущие проверки, открывает работу, читает ответ, ведёт переписку с учеником, принимает,
возвращает на доработку или отклоняет; ученик получает письмо и может ответить.

Один коммит.

Ядро (`kernel/**`, `packages/ui/**`) **не трогаем**. Не хватит — запрос `docs/tasks/requests/…`.

Что не трогаем: группы и потоки, фильтр по группе и ограничение куратора по группам (фаза 4); очередь ручной проверки ответов
`open_text` в тестах (3.6 добавит строки другого вида в ту же очередь); завершение урока по принятой работе (3.6); оценка
баллами; счётчик в меню; письма проверяющим; правка и удаление комментариев; уведомления в мессенджеры.

Риски: пока куратор видит работы **всех** учеников школы — это временно и записывается как правило до фазы 4 (одна функция
`reviewScope`, на неё же опираются тесты изоляции); письмо уходит задачей — доставка и повторы по общему механизму почты;
реплика ученика не меняет статус и не уведомляет проверяющего (очередь — единственный сигнал).

| Раздел `domain.md` | Было | Станет |

| --- | --- |

### Вопросы владельцу

1. **Один коммит** для 3.5 — подходит?
2. **Куратор до потоков** видит и проверяет **все** работы школы; ограничение по группам включается в фазе 4 одной функцией
   (`reviewScope`) — подходит? (Иначе демо фазы — «куратор отправляет на доработку» — невозможно: потоков нет.)
3. **Очередь** — ресурс: по умолчанию «на проверке», старые первыми; фильтры «курс» и «статус», поиск по ученику; фильтр по
   группе — в фазе 4 — подходит?
4. **Переписка**: реплика проверяющего без решения; реплика ученика в `submitted` и `needs_revision`; до 3 файлов к комментарию;
   комментарии не правятся и не удаляются — подходит?
5. **Письмо ученику** о результате проверки (кроме автопринятия), письма проверяющим о новых работах — нет — подходит?
6. **Меню**: пункт «Проверка» для admin, teacher, curator, без счётчика — подходит?
7. **Имена**: API `review.*` (`list`, `get`, `comment`) и `assignment.reply`, право `assessments.review` теперь и у куратора,
   назначение файла `assessments.comment-file`, письмо `assessments.submission-reviewed` — подтвердите.

| Что | Где |
| --- | --- |
| БД | миграция `0017_review_comment_files`: `submission_comment_files` (только добавление) |

| веб | `features/assessments/`: `resources/review.tsx` (фабрика на курсы), `review/review-queue.tsx`, `review/review-screen.tsx`, `comments.tsx` (`CommentThread`, `CommentComposer` — общие для экрана проверки и панели задания), `nav.ts` («Проверка», группа «Обучение»); маршруты `/admin/review`, `/admin/review/$submissionId`; ответ ученика — в `features/learning/assignment/assignment-panel.tsx` |

Отступления от карточки:

- «На проверке» — **сверху**, а не фильтр по умолчанию: «все» в фильтре ресурса — отсутствие фильтра, значение по умолчанию он не умеет;
  порядок «ожидающие сначала, затем по дате отправки» достигает того же без правки ресурс-фреймворка (ядро).
- Подписи курсов в фильтре ресурса — названия кладутся в i18n во время работы (`addResource`): фильтр ресурса знает подписи только по ключам строк.
- Решения несут файлы (`assignment.review` получил `fileIds`) — без этого комментарий с файлом к решению пришлось бы слать отдельно.
- Письмо шлёт подписчик события, а не процедура: автопринятие (нет проверяющего) письма не шлёт.

Проверки: `pnpm check` — ok (api 246); e2e — 52/52 (в 3.4 `assignment.spec` обновлён селектор переписки). Снимки светлой, тёмной темы и 375px просмотрены (очередь, экран проверки).
